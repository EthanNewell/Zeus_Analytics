# Код прозрачности — каркас Django

Запускаемый каркас для команды из пяти разработчиков: Django 5.2 LTS, Python 3.12, MySQL 8.4 и серверные шаблоны.

## Что реализовано

Полный путь MVP: **вход → загрузка таблиц → проверка и сохранение фактов → анализ → реестр → карточка с основаниями → запись проверки сотрудника → CSV-выгрузка.**

- **Импорт** (`imports`): таблицы индикаторов в формате исследования — `.xlsx` или `.csv` (UTF-8, разделитель `;` или `,`). Тип таблицы определяется по строке заголовков. У каждой ячейки сохраняются значение, состояние (есть / «нет данных» / «—»), ячейка-источник и происхождение: жёлтая заливка Excel → «реальное по маркировке автора», формула → «расчётное», остальное → «синтетическое», CSV без разметки → «требует уточнения». Файл проверяется целиком до записи; любая ошибка — ничего не сохраняется, ошибки с номерами строк. Повторная загрузка обновляет записи по ключу, а не дублирует их. Примечания под таблицей («Источники данных: …») становятся паспортом набора.
- **Реестр индикаторов** (`cases/indicators.py`) — одно место, где описаны все 7 таблиц: колонки, ключ, объект, документы, участники, события хронологии, порог и ограничения.
- **Правила** (`analysis/rules`): И1, И2, И3, И4, И6, И8, И10, версия 1.0. Правило читает только исходные факты и само пересчитывает всё, что в таблице было формулой (И8 считает коэффициент заполнения по координатам: площадь контура и наименьший описанный прямоугольник). Результат — статус (`triggered`, `not_triggered`, `insufficient_data`, `not_applicable`), приоритет, объяснение, расчёт, использованные факты и недостающие данные.
- **Запуск анализа** (`AnalysisRun`, `RuleOutcome`) хранится и не перезаписывается; итог по объекту — высокий приоритет / требует проверки / контекстный признак / недостаточно данных / сигналов нет. Колонка «Соответствие индикатору» из таблиц используется как эталон: на наборе исследования 69 из 70 совпадений, единственное расхождение намеренное (совпадение одной фамилии не считается связью).
- **Интерфейс**: обзор, реестр с фильтрами, карточка (почему объект в реестре, хронология, участники, документы, исходные факты по ячейкам, проверка сотрудника), карта контуров и изменённых зон, должностные лица (И10), методика со сверкой, загрузка, выгрузка CSV. Дизайн-система — как у ЭВА-РИСК: синий `#0000e8` и «бумага», шрифт Science Gothic, уровни пятью клетками, происхождение — текстурой. Гравюры — `tools/engravings.py` (Nano Banana + дуотон).
- **Роли** (`accounts/roles.py`): специалист (реестр, карточка, проверка), проверяющий (+ загрузка и анализ), руководитель (+ выгрузка CSV).

Синтетические данные помечены на каждом экране и в выгрузке. Сигнал — повод для проверки, а не вывод о нарушении.

## Быстрый запуск с Docker и MySQL

Нужны Docker Engine/Desktop и Docker Compose v2 с поддержкой `--wait`. Все команды этого раздела выполняются из `Code/`.

```bash
cp .env.example .env
docker compose up -d --build --wait
docker compose exec web python manage.py migrate
docker compose exec web python manage.py bootstrap_roles
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py demo_users
docker compose exec web python manage.py load_tables /путь/к/таблицам --user head
```

Откройте [приложение](http://localhost:8000/). `demo_users` создаёт три учётные записи — `specialist`, `controller`, `head` — со случайными паролями, которые печатает один раз. `load_tables` загружает все `.xlsx`/`.csv` из папки обычным путём импорта и запускает анализ. Таблицы исследования в репозиторий не кладутся: репозиторий публичный, а в реальных строках есть сведения о людях.

`.env.example` содержит только локальные примеры секретов. Для общей среды используйте отдельные значения. Django не загружает `.env` самостоятельно: Compose передаёт переменные процессу.

Код включается в локальный образ при сборке. После изменений выполните `docker compose up -d --build --wait`; после изменений моделей отдельно примените миграции и обновите роли. Том БД сохраняется между пересборками. `docker compose down` останавливает среду; флаг `-v` удаляет данные и для обычной остановки не нужен.

## Запуск без Docker для локальной проверки

SQLite включается только явно и не заменяет MySQL-проверки CI. Нужен Python 3.12; установите инструменты в отдельное окружение:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
export DB_ENGINE=sqlite
export DJANGO_SETTINGS_MODULE=config.settings.local
python manage.py migrate
python manage.py bootstrap_roles
python manage.py createsuperuser
python manage.py demo_users
python manage.py load_tables /путь/к/таблицам --user head
python manage.py runserver 127.0.0.1:8000
```

Этот режим использует `local.sqlite3`, локальный ключ разработки и `DEBUG=True`. Для нативного MySQL установите клиентские заголовки, `pkg-config` и `requirements-mysql.txt`, задайте `DB_ENGINE=mysql` и `MYSQL_*` в окружении. Базовый режим базы — MySQL; SQLite не включается автоматически при ошибке соединения.

## Проверки

```bash
ruff check .
ruff format --check .
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
python manage.py test --settings=config.settings.test
```

Для проверки без сервера БД задайте `DB_ENGINE=sqlite` перед этими командами. CI запускает их с MySQL 8.4 и создаёт отдельную тестовую базу. Пользователю тестовой среды нужны права на её создание; пользователь приложения на стенде не получает таких прав и не использует root.

Зависимости зафиксированы в `requirements.txt`, драйвер — в `requirements-mysql.txt`, инструменты разработки — в `requirements-dev.txt`. При обновлении сначала измените `.in`, затем выполните `pip-compile requirements.in` и `pip-compile requirements-dev.in`, проверьте обе среды. Версия драйвера обновляется отдельно в `requirements-mysql.txt`.

## Модули и владельцы

| Модуль | Назначение | Владелец |
|---|---|---|
| `accounts`, `core`, `config` | Доступ, настройки, CI, стенд | №1 |
| `cases`, `imports` | Объекты, записи индикаторов с происхождением, реестр таблиц, импорт | №2 |
| `analysis` | Правила, запуски, хранимые результаты, итог по объекту | №3 |
| `dashboard`: обзор, реестр, карта | Списки, фильтры, загрузка | №4 |
| `dashboard`: карточка, методика | Основания, хронология, история, выгрузка | №5 |

Набор объектов общий для одного подразделения. Перед добавлением нескольких подразделений потребуется фильтрация всех чтений, записей и выгрузок по принадлежности.

Соглашения: [conventions.md](docs/conventions.md). Подключение модулей: [contracts.md](docs/contracts.md). Стенд и восстановление: [deploy.md](docs/deploy.md). Проверка выпуска: [smoke-check.md](docs/smoke-check.md).

## Проверки состояния

- `/health/live/` — публичный GET, 200 при работающем процессе; без запроса к БД.
- `/health/ready/` — публичный GET, 200 только при доступной БД и отсутствии неприменённых миграций; иначе 503 без технических подробностей.

Проверка контейнера использует live, поэтому первый запуск возможен до миграций. Перед открытием пользовательского трафика обязательна ready. Статика отдаётся WhiteNoise из версии образа, вложения — только через проверяющее права представление.
