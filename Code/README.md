# Код прозрачности — каркас Django

Запускаемый каркас для команды из пяти разработчиков: Django 5.2 LTS, Python 3.12, MySQL 8.4 и серверные шаблоны.

## Что реализовано

Сценарий MVP: **вход → загрузка таблиц → проверка и сохранение фактов → анализ → реестр → карточка с основаниями → запись проверки сотрудника → CSV-выгрузка.**

- **Импорт** (`imports`): таблицы индикаторов в формате исследования — `.xlsx` или `.csv` (UTF-8, разделитель `;` или `,`). Тип таблицы определяется по строке заголовков. У каждой ячейки сохраняются значение, состояние (есть / «нет данных» / «—»), ячейка-источник и происхождение: жёлтая заливка Excel → «реальное по маркировке автора», формула → «расчётное», остальное → «синтетическое», CSV без разметки → «требует уточнения». Файл проверяется целиком до записи; ограничения — до 2 МиБ и 500 строк (вложение к объекту — отдельный лимит, до 5 МБ). При любой ошибке ничего не сохраняется, ошибки показаны с номерами строк. Повторная загрузка обновляет записи по ключу и не создаёт дублей. Примечания под таблицей («Источники данных: …») становятся паспортом набора.
- **Реестр индикаторов** (`cases/indicators.py`) — описание всех 7 таблиц: колонки, ключ, объект, документы, участники, события хронологии, порог и ограничения.
- **Правила** (`analysis/rules`): И1, И2, И3, И4, И6, И8, И10; версия И6 и И10 — 1.1, остальных — 1.0. Правило читает только исходные факты и пересчитывает всё, что в таблице было формулой (И8 считает коэффициент заполнения по координатам: площадь контура и наименьший описанный прямоугольник). И6 сверяет даты покупки и начала процедуры и сам ищет ИНН участника решения среди ИНН покупателя, его учредителей и руководителя (текущих и прежних); колонка «Совпадение ИНН в ЕГРЮЛ» — отметка исследователя, с ней результат сверяется, расхождение показано. Связь через промежуточное юрлицо, которого нет в загруженных данных, берётся из отметки исследователя; автоматическая загрузка выгрузок ЕГРЮЛ — задача пилота. И10 считает эпизоды из комментария исследователя, объекты которых есть в загруженных таблицах других индикаторов (один эпизод не считается дважды); участие лица в эпизоде — по записи исследователя; без таблиц других индикаторов правило опирается на число из таблицы. И2 берёт из таблицы площади зоны и участков владельца. Результат — статус (`triggered`, `not_triggered`, `insufficient_data`), приоритет, объяснение, расчёт, использованные факты и недостающие данные.
- **Запуск анализа** (`AnalysisRun`, `RuleOutcome`) хранится и не перезаписывается; риск объекта — высокий / средний / низкий: наибольший вес среди сработавших индикаторов (веса из таблицы исследования «Индикаторы и источники данных Р1 и Р2»: И4 и И10 высокий; И1, И2, И6, И8 средний; И3 низкий); если ничего не сработало, но данных не хватило, — «нет данных»; иначе «сигналов нет». Решение сотрудника — «Подтверждено», «Не подтверждено» или «Нужны сведения»; объект с окончательным решением уходит из вкладок риска во вкладки решений. Колонка «Соответствие индикатору» из таблиц используется как эталон: на наборе исследования 69 из 70 совпадений (сработало 31, не сработало 35, недостаточно данных 4), расхождение одно: совпадение одной фамилии связью не считается. Набор и ответы составил один автор, независимой разметки нет.
- **Интерфейс** (система из Figma команды, `docs/design-system.md`): главная со сводкой и рекомендациями; объекты — реестр с вкладками риска и решений и карта контуров и изменённых зон (подложка 2ГИС загружается из интернета; в закрытом контуре нужна своя подложка — требование пилота); карточка объекта со сводкой и графом истории (индикаторы → комментарии коллег → решение); аналитика — индикаторы, должностные лица (И10), источники, методика по этапам; история изменений и загрузка; поиск по объектам, документам и событиям; выгрузка CSV.
- **Роли** (`accounts/roles.py`): специалист смотрит реестр и карточки, прикладывает документы, записывает результат своей проверки; проверяющий также загружает таблицы и запускает анализ; руководитель также выгружает результаты в CSV.

Синтетические данные помечены на каждом экране и в выгрузке; строки реальных торгов (`real_data`) такой пометки не имеют. Индикатор — повод для проверки. Решение принимает сотрудник.

## Быстрый запуск с Docker и MySQL

Нужны Docker Engine/Desktop и Docker Compose v2 с поддержкой `--wait`. Все команды этого раздела выполняются из `Code/`.

```bash
cp .env.example .env
docker compose up -d --build --wait
docker compose exec web python manage.py migrate
docker compose exec web python manage.py bootstrap_roles
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py demo_users
docker compose exec web python manage.py load_tables demo_data --user head
docker compose exec web python manage.py load_tables real_data --user head
```

Откройте [приложение](http://localhost:8000/). `demo_users` создаёт три учётные записи — `specialist`, `controller`, `head` — со случайными паролями, которые печатает один раз; при включённом `ENABLE_SYNTHETIC_LOGIN` — ещё открытую демонстрационную запись `12345` / `12345` с правами руководителя. `load_tables` загружает все `.xlsx`/`.csv` из папки через общий импорт и запускает анализ. В `demo_data/` лежат семь таблиц исследования (И1, И2, И3, И4, И6, И8, И10): большая часть строк синтетическая, реальные поля отмечены автором жёлтым. Репозиторий публичный, поэтому ФИО в таблицах сокращены до инициалов, ИНН заменены условными кодами («ИНН П-001» и далее; одинаковый ИНН — один код во всех таблицах, таблица соответствия нигде не хранится). Итог анализа от этого не меняется: 70 записей, 50 объектов, совпадение с разметкой 69 из 70.

В `real_data/` лежит набор реальных торгов: 13 земельных участков Ростовской области из открытых данных ГИС «Торги» (torgi.gov.ru), выгрузка 19.11.2026. Исходную выгрузку (`torgi_61_2026-11-19.json`) делает `tools/torgi_fetch.py`, таблицу в формате И4 собирает `tools/torgi_to_i4.py`. Все 13 строк реальные, имён участников в открытых данных нет. Правило И4 сработало на 9 лотах (аукцион с единственной заявкой, цена договора равна начальной) и не сработало на 4 (цена выросла на 9–576 %). Разметки исследователя у этих строк нет, сверка не меняется. После обеих команд `load_tables` в базе 83 записи и 63 объекта, сработавших правил 40.

`.env.example` содержит только локальные примеры секретов. Для общей среды используйте отдельные значения. Django не загружает `.env` самостоятельно: Compose передаёт переменные процессу.

Код включается в локальный образ при сборке. После изменений выполните `docker compose up -d --build --wait`; после изменений моделей отдельно примените миграции и обновите роли. Том БД сохраняется между пересборками. `docker compose down` останавливает среду; флаг `-v` удаляет данные и для обычной остановки не нужен.

## Запуск без Docker для локальной проверки

SQLite включается только явно и не заменяет MySQL-проверки CI. Нужен Python 3.12; установите инструменты в отдельное окружение:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
export DB_ENGINE=sqlite
export DJANGO_SETTINGS_MODULE=config.settings.local
python manage.py migrate
python manage.py bootstrap_roles
python manage.py createsuperuser
python manage.py demo_users
python manage.py load_tables demo_data --user head
python manage.py load_tables real_data --user head
python manage.py runserver 127.0.0.1:8000
```

Этот режим использует `local.sqlite3`, локальный ключ разработки и `DEBUG=True`. Для нативного MySQL установите клиентские заголовки, `pkg-config` и `requirements-mysql.txt`, задайте `DB_ENGINE=mysql` и `MYSQL_*` в окружении. Базовый режим базы — MySQL; SQLite не включается автоматически при ошибке соединения.

## Проверки

```bash
ruff check .
ruff format --check .
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
python manage.py test --settings=config.settings.test
```

Для проверки без сервера БД задайте `DB_ENGINE=sqlite` перед этими командами. CI (GitHub Actions) на каждое изменение запроса на слияние запускает их с MySQL 8.4 и создаёт отдельную тестовую базу; [последний запуск](https://github.com/EthanNewell/Zeus_Analytics/actions/runs/44457017699) успешен, все 66 тестов прошли. Пользователю тестовой среды нужны права на её создание; пользователь приложения на стенде не получает таких прав и не использует root.

Зависимости зафиксированы в `requirements.txt`, драйвер — в `requirements-mysql.txt`, инструменты разработки — в `requirements-dev.txt`. При обновлении сначала измените `.in`, затем выполните `pip-compile requirements.in` и `pip-compile requirements-dev.in`, проверьте обе среды. Версия драйвера обновляется отдельно в `requirements-mysql.txt`.

## Модули и владельцы

| Модуль | Назначение | Владелец |
|---|---|---|
| `accounts`, `core`, `config` | Доступ, настройки, CI, стенд | №1 |
| `cases`, `imports` | Объекты, записи индикаторов с происхождением, реестр таблиц, импорт | №2 |
| `analysis` | Правила, запуски, хранимые результаты, итог по объекту | №3 |
| `dashboard`: обзор, реестр, карта | Списки, фильтры, загрузка | №4 |
| `dashboard`: карточка, методика | Основания, хронология, история, выгрузка | №5 |

Набор объектов общий для одного подразделения. Перед добавлением нескольких подразделений потребуется фильтрация всех чтений, записей и выгрузок по принадлежности.

Сценарий показа на 3–5 минут: [demo.md](docs/demo.md). Соглашения: [conventions.md](docs/conventions.md). Подключение модулей: [contracts.md](docs/contracts.md). Стенд и восстановление: [deploy.md](docs/deploy.md). Проверка выпуска: [smoke-check.md](docs/smoke-check.md).

## Проверки состояния

- `/health/live/` — публичный GET, 200 при работающем процессе; без запроса к БД.
- `/health/ready/` — публичный GET, 200 только при доступной БД и отсутствии неприменённых миграций; иначе 503 без технических подробностей.

Проверка контейнера использует live, поэтому первый запуск возможен до миграций. Перед тем как открыть сервис пользователям, проверьте ready. Статика отдаётся WhiteNoise из версии образа, вложения — только через проверяющее права представление.

## Окно входа

Форма доступна по адресу `/accounts/login/`. Django проверяет учётные данные и отдаёт форму даже при отключённом JavaScript. Исходник карточки находится в `frontend/src/auth-form.tsx`, стили — в `frontend/src/theme.css`, компоненты shadcn/ui — в `frontend/src/components/ui/`.

Команда `python manage.py demo_users` создаёт демонстрационную учётную запись с ролью «Руководитель», если включено `ENABLE_SYNTHETIC_LOGIN` (локально включено всегда, на стенде — переменной окружения `ENABLE_SYNTHETIC_LOGIN=1`). Введите `12345` в поля «Почта» и «Пароль», чтобы открыть главную страницу.

В разделе «Объекты» или в карточке объекта нажмите «Загрузить документ» (из карточки документ привязывается к объекту). Можно выбрать несколько файлов, указать тип, источник и описание каждого. Загруженные документы доступны для скачивания в реестре и через поиск.

После изменения формы или стилей пересоберите шаблон и статику и включите результат в коммит.

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm run build
```
