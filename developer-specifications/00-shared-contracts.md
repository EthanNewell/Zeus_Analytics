# Общие контракты №2–5

Эта спецификация дополняет [исходный каркас](sources/Каркас_Django_Код_Прозрачности.md). Код ещё предстоит реализовать. Имена сервисов и дополнительные enum ниже — предлагаемая единая редакция; окончательные изменения 14 ноября №1–3 фиксируют в `Code/docs/contracts.md`, одновременно обновляя примеры и потребителей. Смысл четырёх статусов, происхождение и разделение обязанностей обязательны по исходным материалам.

## 1. Владельцы и границы модулей

| Путь | Владелец | Ответственность |
|---|---|---|
| `Code/accounts/`, `Code/core/`, `Code/config/` | №1 | Пользователь, права, настройки, общие ошибки и request ID |
| `Code/cases/` | №2 | Факты, участники, связи, документы и история проверок |
| `Code/imports/` | №2 — данные; №4 — формы, views, шаблоны | Приём CSV, валидация, происхождение, итог загрузки |
| `Code/analysis/` | №3 | Правила, снимок входов, запуски, результаты, POST запуска |
| `Code/dashboard/` | №4 — реестр; №5 — карточка и экспорт | Сбор данных сервисов и запросов чтения для интерфейса |
| `Code/templates/base.html`, `Code/static/` | №4 | Общий макет и стили; №5 добавляет компоненты карточки |

`views.py` проверяет HTTP и разрешения, `forms.py` — ввод, `services.py` — запись, `selectors.py` — согласованные запросы чтения. `analysis` использует факты `cases`; `cases` не зависит от `dashboard` или `analysis`. Общие `dashboard/urls.py` и `selectors.py` координирует №4, дополняет №5 небольшими PR. Миграции `cases`/`imports` координирует №2, `analysis` пишет №3 с проверкой №2, `accounts` — №1.

## 2. Типы и словари

UUID — идентификаторы случаев, источников, загрузок, запусков и результатов. Кадастровый номер и ИНН — строки. Дата — `YYYY-MM-DD`; время — ISO 8601 с часовым поясом, в интерфейсе Europe/Moscow. Деньги и площади — Decimal с обозначением единиц. Неизвестное значение отличается от `0`, `False` и неприменимости.

| Поле | Значения и смысл |
|---|---|
| `RuleResult.status` | `triggered` — сработал; `not_triggered` — не сработал; `insufficient_data` — недостаточно данных; `not_applicable` — не применим |
| `provenance` | `author_marked_real` — реальное по маркировке автора; `synthetic`; `calculated`; `unknown` |
| `value_state` (предложение) | `present`, `missing`, `not_applicable`; для подтверждённого отсутствия события — явный факт, а не пустая ячейка |
| `verification_status` (предложение) | `unverified`, `verified`, `conflicting`; маркировка автора сама по себе не даёт `verified` |
| `priority` (предложение) | `high`, `medium`, `low`, `none`; при недостаточных данных — `none`, UI «не определён» |
| `Review.outcome` (предложение) | `grounds_confirmed` — основания для дальнейшей проверки подтверждены; `not_confirmed` — предположение не подтвердилось; `needs_information` — нужны дополнительные сведения |

Полнота выводится из недостающих обязательных полей; не выводится из приоритета. Область неизвестного происхождения также показывается отдельно. `is_demonstration=true`, если вывод прямо или через расчёт использует синтетический факт. Распространение признака по расчётным зависимостям обязательно. `unknown` не становится ни «реальным», ни «синтетическим» автоматически.

## 3. Минимальная модель фактов

№2 выбирает нормализованную физическую схему, сохраняющую следующие связи:

| Сущность | Минимальный смысл и поля |
|---|---|
| `Case` | UUID, устойчивый внешний ключ, территория, связь с участком/участками и событиями, даты создания/обновления |
| `LandPlot` | Кадастровый номер, адрес при наличии; категория и ВРИ — разные факты с историей |
| `Event` | Тип, дата/период, участок, участники и их роли, документ-основание; неизвестная дата остаётся неизвестной |
| `Party` | Внешний идентификатор, тип лица, наименование; ИНН при наличии; совпадение имени не объединяет лиц |
| `Relationship` | Участники, вид связи, период действия, источник, статус подтверждения; участие в решении фиксируется отдельным фактом |
| `Evidence` | UUID, тип, название, реквизиты/URL или защищённый файл, дата документа и получения, происхождение и основание использования при наличии |
| `Fact` или равнозначная модель | Устойчивый ID факта, субъект и поле, значение и состояние, происхождение, исходные файл/лист/ячейка, ссылка на Evidence, статус сверки; для расчёта — входные fact ID и версия |
| `ImportBatch` | Автор/время, checksum, версия формата, статус, счётчики, ошибки с номерами строк, ссылки на исходную и повторную загрузку |
| `Review` | UUID, случай, выбранный запуск/результат при наличии, исход, обоснование, документы, автор и время сервера, ключ защиты от повторного POST |

Факт, на который ссылается результат, неизменяем либо имеет неизменяемую версию. Сверка создаёт новую версию с источником, сохраняя прежнюю. Для запуска анализа сохраняется снимок входов. Связь документа с конкретным фактом обязательна: списка файлов на весь случай недостаточно. Исходные сведения, выводы системы и действия сотрудника хранятся раздельно.

## 4. Импорт и CSV

Обязательный формат приложения — CSV. Прямое чтение Excel не входит в MVP: №2 готовит воспроизводимое преобразование/инструкцию из семи файлов. Источник, лист, ячейка и происхождение значимых полей сохраняются явно; цвет не используется как единственный носитель происхождения.

Предложение транспортного формата: UTF-8 с допустимым BOM, разделитель `;`, кавычки `"`, первая строка — заголовки, дата ISO, десятичный разделитель `.`. №2 публикует полный словарь **до подключения формы**, включая: имена и порядок колонок, типы/единицы, обязательность, представление пустого значения и «не применимо», внешние ключи связей, происхождение каждого значимого поля, ключи дублей, версию формата. Структурные ошибки файла отклоняют загрузку; отсутствие предметного факта допустимо, если оно явно представлено и ведёт к неполному анализу.

Нужны три файла-примера: корректный, структурно ошибочный и допустимый неполный. Номер ошибки — физический номер строки с учётом строки заголовка; если разрешены переносы в CSV-поле, возвращается номер начала записи. Ошибка содержит `row`, `field`, `code`, `message`; значение строки целиком в журнал не пишется.

Предлагаемый сервис:

```text
imports.services.import_csv(file, *, actor, idempotency_key) -> ImportOutcome
ImportOutcome:
  batch_id, status: completed | rejected | duplicate,
  case_ids[], created_count, duplicate_count,
  errors[{row, field, code, message}], original_batch_id?
```

Порядок: проверка размера/формата → полная валидация → запись предметных данных одной транзакцией. При ошибке сохраняется только журнал отклонённой загрузки; случаев/фактов/связей из неё нет. Блокировка/ограничения БД защищают от одновременных дублей. Для MVP предлагаем: повтор идентичного файла возвращает исходный batch; одинаковый внешний ключ и те же значения пропускаются; новые строки добавляются; разные значения под тем же ключом отклоняют весь пакет с `CONFLICTING_FACT`, старые данные сохраняются. Сверка конфликтов — отдельная операция, без автоматической перезаписи. Равенства кадастрового номера недостаточно для дубля случая или события.

## 5. Анализ, выборка и результат

Предлагаемые интерфейсы:

```text
cases.selectors.get_case_facts(case_id, *, revision=None) -> CaseFacts
dashboard.selectors.select_cases(filters, *, actor) -> QuerySet[Case]
analysis.services.run_analysis(*, case_ids, selection, actor, idempotency_key) -> AnalysisRun
cases.services.add_review(*, case_id, outcome, justification,
  evidence_ids, analysis_run_id, actor, idempotency_key) -> Review
```

`select_cases` — единая семантика отбора реестра и экспорта. `selection` анализа хранит территорию, период и явный критерий включения событий; дополнительно фиксируются обработанные case ID. Период имеет включённые границы, фильтрует события, а не дату импорта. Отсутствующая дата события не приписывается к периоду; число исключённых неполных записей показывается. Запуск из реестра обрабатывает всю явно выбранную выборку, а не только страницу таблицы. Все параметры проверяются сервером; скрытые поля формы не считаются доверенными.

`AnalysisRun`: UUID, автор/время, состояние `running|completed|failed`, версия набора правил, параметры (включая временное окно), область отбора, снимок/неизменяемые версии входов, список случаев, длительность. Технический сбой даёт `failed`, не `not_triggered`. Незавершённый запуск не подменяет предыдущие успешные результаты. Новый осознанный запуск создаёт новую запись; повтор одного POST с тем же ключом возвращает прежний запуск.

`RuleResult`: `case_id`, `analysis_run_id`, `rule_code`, `rule_version`, `status`, `priority`, `explanation`, `used_fact_ids[]`, `evidence_ids[]`, `missing_fields[]`, `is_demonstration`. Дополнительно — выполненные/невыполненные условия, полнота и предупреждения о конфликтах/происхождении. Уникальность `(analysis_run_id, case_id, rule_code)`.

Предложение для отбора актуальных результатов: реестр показывает последний успешный результат **на случай**, с ID/временем запуска; фильтры по правилам применяются к этому набору. Карточка позволяет открыть исторический запуск. Сводка считает уникальные случаи, а не количество RuleResult. Запуск на старой ревизии явно помечается «данные обновлены, требуется повторный анализ».

Приоритеты пилота: Р1.6 `triggered` → `high`; Р1.2 `triggered` → `medium` как земельно-правовая аномалия; только Р1.8 `triggered` → `low` как контекст, без самостоятельного коррупционного сигнала; остальные результаты → `none`. Приоритет случая — максимум среди его результатов одного выбранного запуска. Это настройка отбора для проверки, не оценка вероятности коррупции. До фиксации №1 и №3 могут уточнить таблицу, сохранив запрет высокого приоритета от одного Р1.8.

## 6. HTTP, права и формы

Имена маршрутов соответствуют исходному каркасу. Это внутренние Django views, JSON API не требуется.

| Метод и URL | Имя | Владелец |
|---|---|---|
| GET `/cases/` | `dashboard:case_list` | №4 |
| GET `/cases/<uuid:case_id>/` | `dashboard:case_detail` | №5 |
| POST `/cases/<uuid:case_id>/reviews/` | `dashboard:review_create` | №5, сервис №2 |
| POST `/cases/<uuid:case_id>/evidence/` | `dashboard:evidence_create` | №5, сервис №2; дополнительный маршрут этого пакета |
| GET/POST `/imports/` | `imports:upload` | №4, сервис №2 |
| GET `/imports/<uuid:batch_id>/` | `imports:detail` | №4 |
| POST `/analysis/run/` | `analysis:run` | №3, кнопка №4 |
| GET `/exports/cases.csv` | `dashboard:case_export` | №5 |
| GET `/evidence/<uuid:evidence_id>/download/` | `dashboard:evidence_download` | №5 |

Все данные требуют входа и разрешений. Предлагаемые коды, окончательно выдаваемые №1 группе `Specialist`: `cases.view_case`, `cases.view_evidence`, `cases.add_evidence`, `cases.add_review`, `imports.add_importbatch`, `imports.view_importbatch`, `analysis.add_analysisrun`, `cases.export_case` (последнее — custom permission). Администратор действует по выданным правам. Для просмотра карточки источников нужны соответствующие права; экспорт и импорт проверяют также доступ к каждому случаю. Одна организация и общий набор случаев — допущение MVP.

Без входа — штатный переход на вход; без права — 403; отсутствующий/недоступный UUID — 404 без раскрытия данных. POST с CSRF, валидацией формы и защитой от повторной отправки; после успеха — redirect. GET не запускает анализ и не сохраняет проверку. Пользовательские строки экранируются; файлы выдаются защищённым view, без публичного `media/`. Результат проверки нельзя редактировать удалением истории: исправление добавляет новую запись.

## 7. Фильтры и экспорт

Предлагаемые GET-параметры: `q` (кадастровый номер/ID случая), `territory`, `date_from`, `date_to`, `rule_code`, `rule_status`, `priority`, `review_outcome`, `is_demonstration`, `page`. №4 фиксирует их вместе с №3 и №5. `review_outcome` означает последний исход проверки по случаю; «не проверен» — отдельное значение. При сочетании `rule_code` и `rule_status` оба условия относятся к **одному** результату правила. Фильтр происхождения относится к показанным результатам; смешанный случай остаётся явно помеченным. Отсутствие анализа отличается от отрицательного результата.

CSV выгружает всю отфильтрованную выборку без пагинации. Одна строка — один результат правила выбранного актуального запуска; для случая без анализа — строка с пустыми полями правила и явным состоянием `not_analyzed`. Минимальные колонки: `case_id`, `cadastral_number`, `territory`, `analysis_run_id`, `analysis_created_at`, `rule_code`, `rule_version`, `rule_status`, `priority`, `explanation`, `missing_fields`, `used_fact_ids`, `evidence_ids`, `is_demonstration`, `provenance_warning`, `review_outcome`, `review_author`, `review_created_at`, `review_justification`. Добавить признак устаревших результатов. Поля списков сериализуются JSON-массивами внутри корректно экранированной CSV-ячейки. Последняя проверка и её время не подменяют результат анализатора.

UTF-8 с BOM, `;`, безопасное имя файла, корректное quoting строк. Текстовые значения, которые табличный редактор может выполнить как формулу (`=`, `+`, `-`, `@`, в том числе после начальных управляющих/пробельных символов), нейтрализуются при экспорте без изменения исходных данных; политика описывается в инструкции. Внешние/закрытые документы в CSV не встраиваются: передаются идентификаторы/разрешённые ссылки.
