# Каркас Django, вход, соглашения, интеграция, CI и стенд

Рабочее техническое задание для разработчика №1 проекта «Код прозрачности».

Период: 14–20 ноября 2026 года. Финальный релиз — к вечеру 19 ноября. Проверяющий — разработчик №2; сквозную проверку координирует №5. Основание — [пайплайн проекта](Пайплайн_Код_Прозрачности_20-11.md).

Это план реализации и приёмки. Указанные ниже файлы, команды и маршруты описывают целевой каркас; код приложения и работающий стенд в рамках этого документа не создавались.

## 1. Результат работы №1

Команда получает единый Django-проект, который запускается по README с MySQL, требует входа для доступа к данным, позволяет независимо разрабатывать пять модулей и воспроизводимо выпускать проверенную версию на стенд.

К концу 14 ноября должны работать запуск, миграции, вход, выход и закрытая стартовая страница. К концу 15 ноября — первый сквозной путь: CSV → MySQL → одно правило → реестр → карточка. Содержимое этого пути разрабатывают владельцы соответствующих модулей; №1 отвечает за их совместимость и выпуск.

## 2. Технологические решения

| Область | Принятое решение |
|---|---|
| Приложение | Один Django-проект, Django Templates, небольшой объём JavaScript |
| Python | Ветка 3.12; одинаковая среда в контейнере приложения и CI |
| Django | 5.2 LTS; при первоначальной фиксации зависимостей — проверенный актуальный патч ветки |
| База данных | MySQL 8.4, InnoDB, `utf8mb4`, строгий SQL-режим |
| Драйвер | `mysqlclient` |
| Вход | Django Authentication, серверные сессии, логин и пароль |
| Проверки | Ruff, встроенный тестовый раннер Django, интеграционные тесты с MySQL |
| Локальный запуск | Docker Compose: приложение и MySQL |
| Стенд | Docker Compose на одном сервере: HTTPS-прокси → Gunicorn → Django → MySQL |
| CI | GitHub Actions как базовый вариант; при другом Git-хостинге сохраняется тот же набор проверок |
| Выпуск | Сначала ручной воспроизводимый выпуск проверенного образа по инструкции; автоматизация — после первого рабочего выпуска |

Django 5.2 LTS имеет поддержку безопасности до апреля 2028 года. Версия патча фиксируется в файле зависимостей; плавающий диапазон не используется для выпуска. [Поддерживаемые версии Django](https://www.djangoproject.com/download/).

MySQL настраивается со строгим режимом, чтобы ошибки усечения значений приводили к отказу операции. Работу приложения проверяем именно с MySQL. [Настройки MySQL для Django](https://docs.djangoproject.com/en/5.2/ref/databases/#mysql-notes).

├── imports/                   # №2: загрузки, валидация, дубли
├── analysis/                  # №3: правила, запуски и результаты
│   └── rules/

├── requirements.in
├── requirements.txt           # точные версии всех зависимостей приложения
├── requirements-dev.in
├── requirements-dev.txt       # инструменты разработки, совместимые с основным lock-файлом

В каждом Django-приложении создаются `apps.py`, необходимые `models.py`, `urls.py`, `views.py`, каталог `migrations/` и тесты. Пакеты Python получают `__init__.py`. Папки с пользовательскими файлами и собранной статикой создаются при запуске и не попадают в Git.

Распределение логики: `views.py` обрабатывает HTTP и права, `forms.py` проверяет ввод, `services.py` выполняет операции записи, `selectors.py` содержит повторно используемые запросы чтения. Правила вынесены в `analysis/rules/`. Дополнительные слои вводятся только при наличии кода, которому они нужны.

## 4. Настройки и локальная среда

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings.local`, `test` или `staging` |
| `DJANGO_SECRET_KEY` | Отдельный секрет для каждой среды; обязательный на стенде |
| `DJANGO_ALLOWED_HOSTS` | Разрешённые имена хостов, без `*` на стенде |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Точные HTTPS-origin стенда |
| `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` | Подключение приложения к БД |
| `MYSQL_HOST`, `MYSQL_PORT` | `db:3306` внутри Compose; адрес сервиса в CI задаётся отдельно |
| `MYSQL_ROOT_PASSWORD` | Только инициализация локального контейнера/тестовой БД; приложение его не использует |
| `APP_VERSION` | SHA коммита или тег образа для журналов и выпуска |
| `MAX_IMPORT_BYTES`, `MAX_IMPORT_ROWS` | Ограничения загрузки; окончательные значения определяются прогоном 15 ноября |
| `LOG_LEVEL` | Уровень журналирования |

`.env` исключается из Git и контекста Docker-сборки. В `staging.py` отсутствие секрета или параметров БД останавливает запуск. `DEBUG` для стенда задан как `False`, а не вычисляется через `bool()` от строки.

Общие настройки: `LANGUAGE_CODE = "ru-ru"`, `TIME_ZONE = "Europe/Moscow"`, `USE_TZ = True`. Моменты времени сохраняются в UTC, интерфейс показывает московское время. Даты земельных событий без времени остаются датами.

### Путь первого запуска

После реализации файлов разработчик должен пройти из `Code/` такой путь:

```bash
cp .env.example .env
# Заполнить значения локальных секретов в .env.
docker compose up -d --build --wait
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py bootstrap_roles
```

`bootstrap_roles` — команда №1: повторный запуск создаёт недостающие группы и обновляет их права без создания пользователей и сброса паролей. Команда запускается после миграций. Условия готовности контейнеров проверяют MySQL и живость приложения; готовность к пользовательскому сценарию проверяется после миграций.

Зависимость от MySQL задаётся через проверку готовности сервиса, а не через фиксированную задержку старта. [Порядок запуска Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/).

## 5. Вход и доступ

### Пользователь и сессия

- До первой миграции определить `accounts.User` на основе `AbstractUser` и `AUTH_USER_MODEL = "accounts.User"`. Вход выполняется по `username`; все ссылки на пользователя используют модель из настроек.
- Использовать стандартные `LoginView`, `LogoutView`, форму аутентификации и валидаторы паролей. Сессии хранятся в БД.
- После входа перенаправлять в реестр либо на проверенный локальный `next`. Внешний адрес в `next` не принимается.
- Выход — POST-форма с CSRF. GET-запрос не завершает сессию.
- Учётные записи создаёт администратор. Учётные данные передаются отдельно от репозитория.

Пользовательская модель создаётся в первой миграции приложения `accounts`, до миграций зависимых приложений. [Рекомендация Django для нового проекта](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project).

Серверное поведение входа и выхода опирается на штатные представления Django. [Документация аутентификации](https://docs.djangoproject.com/en/5.2/topics/auth/default/#all-authentication-views).

### Матрица доступа

| Действие | Не вошёл | Специалист | Администратор |
|---|---|---|---|
| Открыть страницу входа | Да | Да | Да |
| Реестр, карточка, источники и CSV-выгрузка | Перенаправление на вход | Да | Да |
| Импорт и запуск анализа | Перенаправление на вход | Да | Да |
| Добавить результат проверки сотрудника | Перенаправление на вход | Да, от своего имени | Да, от своего имени |
| Управление пользователями и группами | Нет | Нет | Да, при соответствующих правах |
| Изменить исходные данные через Django Admin | Нет | Нет | Только по отдельно выданным правам |

Предположение MVP: одно подразделение и общий набор случаев для его специалистов. При появлении нескольких подразделений требуется модель принадлежности и фильтрация доступа во всех запросах и выгрузках.

Роль специалиста задаётся группой `Specialist`. Сам факт входа не выдаёт права на операции. Для изменения данных проверяются конкретные разрешения на сервере; пользователь без нужного права получает 403. Кнопки в шаблонах отражают эти же проверки.

Доступ к представлениям по умолчанию закрывается `LoginRequiredMiddleware`, установленным после `AuthenticationMiddleware`. Исключения задаются явно: вход и технические проверки состояния. [Поведение middleware](https://docs.djangoproject.com/en/5.2/ref/middleware/#django.contrib.auth.middleware.LoginRequiredMiddleware).

Вложения выдаются через защищённое представление после проверки доступа к случаю. Общедоступный URL папки `media/` на стенде не настраивается.

### Маршруты

| Метод и URL | Имя маршрута | Назначение / владелец |
|---|---|---|
| GET/POST `/accounts/login/` | `accounts:login` | Вход / №1 |
| POST `/accounts/logout/` | `accounts:logout` | Выход / №1 |
| GET `/` | `home` | Переход в реестр / №1 |
| GET `/cases/` | `dashboard:case_list` | Реестр и фильтры / №4 |
| GET `/cases/<uuid:case_id>/` | `dashboard:case_detail` | Карточка / №5 |
| POST `/cases/<uuid:case_id>/reviews/` | `dashboard:review_create` | Сохранение проверки / №5, сервис №2 |
| GET/POST `/imports/` | `imports:upload` | Форма и обработка загрузки / №4, сервис №2 |
| GET `/imports/<uuid:batch_id>/` | `imports:detail` | Итог загрузки и ошибки / №4 |
| POST `/analysis/run/` | `analysis:run` | Запуск с явно заданной областью анализа / №3 |
| GET `/exports/cases.csv` | `dashboard:case_export` | Выгрузка с текущими фильтрами / №5 |
| GET `/evidence/<uuid:evidence_id>/download/` | `dashboard:evidence_download` | Защищённый файл / №5 |
| GET `/health/live/` | `core:live` | Процесс отвечает; без обращения к БД / №1 |
| GET `/health/ready/` | `core:ready` | Подключение к БД и актуальность миграций / №1 |

Технические проверки возвращают только 200 или 503 и краткий статус. Проверка readiness выполняет проверку соединения и плана миграций; названия таблиц, исключения и секреты не выдаются. Её частоту ограничиваем на прокси. Административные URL доступны только сотрудникам с нужными правами.

## 6. Общие соглашения

| Область | Соглашение |
|---|---|
| Код | Английские идентификаторы; русские подписи интерфейса; Ruff как единый форматтер и линтер |
| Идентификаторы | UUID для случаев, загрузок, источников и запусков; кадастровый номер и ИНН хранятся строками |
| Даты в обмене | `YYYY-MM-DD`; момент времени — ISO 8601 с часовым поясом |
| Числа | `Decimal` для денег и площадей; формат и единицы закреплены в CSV-контракте |
| Неизвестные значения | Отсутствие данных хранится явно; `False` и `0` не подменяют неизвестное значение |
| Изменения состояния | Только POST с CSRF; после успешной формы — перенаправление |
| Транзакции | Импорт сначала полностью валидируется, затем сохраняется в одной транзакции; ошибочная загрузка не оставляет частичных предметных данных |
| Повторы | Дедупликация импорта по согласованным ключам; повторный POST не создаёт незаметных дублей |
| Ошибки | Предсказуемые сообщения пользователю; технические подробности — в журнале с идентификатором запроса |
| Журналы | Время, уровень, модуль, request ID, версия приложения; без паролей, cookie, токенов и содержимого загруженных строк |
| История проверки | Автор и время назначаются сервером; записи добавляются, исходные факты и результаты анализа не перезаписываются |
| Шаблоны | Наследование от `base.html`, namespaced URL, экранирование пользовательского текста |
| Файлы | Ограничение размера и допустимых форматов; внутреннее имя формирует сервер; оригинальное имя — только метаданные |

Для каждого значимого факта сохраняются происхождение, исходный файл/лист/ячейка при наличии, источник и статус сверки. Происхождение принимает одно из значений: `author_marked_real`, `synthetic`, `calculated`, `unknown`. Маркировка автора не означает независимую проверку. У расчётного факта сохраняются входы и версия расчёта.

Ветки короткие, с описанием задачи; основная ветка — `main`. У PR есть результат, способ проверки и сведения о миграциях. Проверка напарником и успешный CI обязательны перед слиянием. В Git не попадают БД, `.env`, загруженные документы и локальные окружения.

Миграции предметных приложений координирует №2; миграции `accounts` — №1. Изменение общей модели сначала согласуется с потребителями. Конфликт миграций проверяется на чистой БД и на обновлении предыдущей рабочей версии.

## 7. Интеграция пяти модулей

### Владельцы данных и границы

| Модуль | Ответственность | Контракт для остальных |
|---|---|---|
| `accounts`, `core` / №1 | Пользователь, права, окружение, общая обработка ошибок | Пользователь из `AUTH_USER_MODEL`, разрешения, идентификатор запроса |
| `cases` / №2 | `Case`, `LandPlot`, `Event`, `Party`, `Relationship`, `Evidence`, история проверки | Согласованная схема, чтение фактов, сервис добавления проверки |
| `imports` / №2 | `ImportBatch`, валидация, происхождение, дедупликация | Сервис загрузки возвращает batch ID, созданные case ID или структурированные ошибки |
| `analysis` / №3 | `AnalysisRun`, `RuleResult`, версии правил | Сервис анализа принимает case ID и параметры отбора, возвращает run ID и результаты |
| `dashboard` / №4 и №5 | Формы, реестр, карточка, выгрузки | Использует сервисы записи и согласованные запросы чтения |

Предметные модели не импортируют представления или шаблоны. `cases` не зависит от `dashboard`; `analysis` использует факты из `cases`; `dashboard` собирает данные модулей. Настройки и общие утилиты не содержат земельных правил.

### Контракты, фиксируемые 14 ноября

1. **CSV:** имена колонок, кодировка, разделитель, форматы дат и чисел, обязательность, ключи дублей, происхождение полей; по одному корректному, ошибочному и неполному примеру. Итог загрузки содержит номера строк и коды ошибок.
2. **Результат правила:** `case_id`, `analysis_run_id`, `rule_code`, `rule_version`, `status`, `priority`, `explanation`, `used_fact_ids`, `evidence_ids`, `missing_fields`, `is_demonstration`.
3. **Контекст запуска:** территория, период, условия отбора, версия набора правил, снимок обработанных фактов и источников либо ссылки на их неизменяемые версии. Одного времени запуска недостаточно для воспроизведения результата.
4. **Проверка сотрудника:** case ID, один из трёх исходов, обоснование, ссылки на документы; автор и время — серверные поля. Новая запись сохраняет прежние.
5. **Соглашение кодов:** соответствие индикаторов И из Excel и правил Р1 фиксируется отдельной таблицей. Автоматического равенства кодов нет.

Статусы правила строго перечислены: `triggered` — сработал; `not_triggered` — не сработал; `insufficient_data` — недостаточно данных; `not_applicable` — не применим. Приоритет и полнота данных хранятся отдельно от статуса. Контекстный признак Р1.8 самостоятельно не даёт высокого приоритета.

`is_demonstration` устанавливается, если вывод использует синтетический факт или расчёт на его основе. Неуточнённое происхождение показывается отдельной пометкой. Ни интерфейс, ни CSV не должны представлять эти записи как подтверждённые реальные нарушения.

### Порядок сборки

14 ноября №1 публикует интерфейсы модулей и закрытую стартовую страницу; №2 — миграции и минимальный пример; №3 — результат одного правила в согласованном формате; №4 и №5 — шаблоны на этих данных. Временная заглушка видимо обозначается и не засчитывается как готовая функция.

15 ноября интегрируется один полный сценарий на MySQL. После его проверки подключаются остальные правила, история сотрудника и выгрузка. CI проверяет текущую объединённую версию при каждом PR; выпуск на стенд сопровождается коротким прогоном пользовательского пути.

## 8. CI

Базовый вариант — `.github/workflows/ci.yml` в корне репозитория. Workflow запускается на PR и изменения `main`, работает с `Code/` как рабочим каталогом и использует Ubuntu runner. Права токена — чтение содержимого. Секреты стенда для проверки PR не нужны.

В job поднимается отдельный MySQL той же ветки, что на стенде, с проверкой готовности. Django создаёт и уничтожает тестовую БД; соответствующие права существуют только у временной учётной записи CI. Основные журналы тестов сохраняются при ошибке. [Сервисные контейнеры GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers).

Последовательность обязательных проверок после установки зафиксированных зависимостей:

```bash
ruff check .
ruff format --check .
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
python manage.py migrate --noinput --settings=config.settings.test
python manage.py test --settings=config.settings.test
docker build -t transparency-ci .
```

| Группа проверок | Что должно подтвердиться | Ответственный |
|---|---|---|
| Вход и права | Неверный пароль, неактивный пользователь, отсутствие разрешения, безопасный `next`, выход только POST | №1 |
| Закрытые данные | Гость не получает карточку, CSV и вложение; новый маршрут закрыт по умолчанию | №1 и автор маршрута |
| CSRF | Запись без CSRF отклоняется; проверяется клиентом с принудительной CSRF-проверкой | №1 |
| MySQL и импорт | Чистые миграции, Unicode, дубли, отсутствие частичного импорта, корректные ограничения БД | №2 |
| Правила | Все четыре статуса, границы дат, исключения, сохранение версии и объяснений | №3 |
| Сквозной путь | Вход → импорт → анализ → список → карточка → проверка сотрудника → выгрузка | №5 совместно с владельцами |
| Повторный запуск | Результаты и история не теряются; повторный импорт не размножает случаи | №2 и №3 |

Первый PR каркаса проходит проверки запуска, миграций и входа. По мере появления модулей в обязательный набор добавляются их содержательные тесты. Неуспешные проверки не отключаются ради слияния. Проверка сборки образа включается в CI с первого Dockerfile.

## 9. Стенд и выпуск

### Состав стенда

Один сервер с Docker Compose. Снаружи доступен только HTTPS-прокси; Gunicorn и MySQL доступны во внутренней сети. БД, вложения и резервные копии размещаются в постоянных томах/каталогах; приложение запускается непривилегированным пользователем. Статика собирается в образ при сборке и отдаётся прокси из соответствующей версии. Вложения выдаёт защищённое представление.

Настройки стенда: `DEBUG=False`, явные `ALLOWED_HOSTS` и trusted origins, HTTPS, защищённые cookie сессии и CSRF. Заголовку HTTPS доверяем только от собственного прокси, который перезаписывает входящее значение. На входе ограничивается частота попыток. Ошибки показывают нейтральную страницу и request ID.

Перед первым выпуском выполняется `manage.py check --deploy --settings=config.settings.staging` с настоящими настройками среды. Замечания устраняются либо для них фиксируется обоснованное решение. [Проверки Django перед развёртыванием](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

### Данные, которые №1 фиксирует для первого выпуска

| Параметр | Где зафиксировать |
|---|---|
| Git-хостинг и URL репозитория | README |
| Сервер, домен и HTTPS | `docs/deploy.md` |
| Реестр образов и схема тегов по SHA | `docs/deploy.md` |
| Хранение секретов и ответственный за доступ | Инструкция без значений секретов |
| Путь резервных копий, срок хранения, порядок восстановления | `docs/deploy.md` |
| Лимиты файла, строк и допустимое время анализа | README после измерения 15 ноября |

Эти параметры пока не заданы в исходных материалах. До получения сервера команда использует локальную среду; это не заменяет проверку доступности общего стенда.

### Выпуск конкретной версии

1. Выбрать коммит с успешным CI, собрать образ один раз и зафиксировать его SHA/digest. Эта же версия проходит проверку и используется для демонстрации.
2. Включить техническую страницу на прокси, чтобы остановить новые записи. Сделать согласованную резервную копию MySQL и вложений; сохранить предыдущий образ и конфигурацию.
3. Проверить параметры среды, план миграций и совместимость изменений со старой версией. Применить миграции один раз отдельной командой, до запуска пользовательского трафика.
4. Запустить приложение из выбранного образа. При первом выпуске создать роли и администратора отдельными командами. Загрузку демоданных выполнять явно; рестарт приложения не меняет данные.
5. Проверить `/health/live/` и `/health/ready/`, вход, закрытые данные и основной сценарий. После успеха снять техническую страницу и повторить короткую проверку через внешний HTTPS-адрес.
6. Записать версию, время, исполнителя, миграции и итог проверки в журнал выпуска. При ошибке оставить техническую страницу и выполнить план восстановления.

Миграции не запускаются каждым Gunicorn worker или при каждом рестарте контейнера. Ошибка миграции останавливает выпуск.

### Откат и восстановление

Если схема совместима, вернуть предыдущий образ и проверить приложение. Откат образа сам по себе не отменяет миграции. Для несовместимого изменения использовать проверенный план возврата схемы либо восстановить согласованную копию БД и вложений, пока запись остановлена. После открытия записи восстановление старой копии требует учесть появившиеся данные.

До 19 ноября №2 восстанавливает копию в отдельную БД, а №1 подтверждает запуск приложения на ней. Резерв демонстрации: локальный Compose, тот же зафиксированный образ и подготовленные демоданные. Скриншоты или видео сопровождают резервный сценарий.
