# ТЗ №2. Данные, MySQL, импорт и демонабор

**Исполнитель:** разработчик №2. **Принимает:** №1; контракты фактов проверяет №3. Прочитать [общие контракты](00-shared-contracts.md). Результат: из корректного CSV получаются связанные, проверяемые факты; ошибки и повторы не портят БД; другой разработчик воспроизводит загрузку.

## 1. Область ответственности

Реализовать `Code/cases/`, модели и сервисы `Code/imports/`, миграции этих приложений, тестовые данные и команды их загрузки. Форму и HTTP импорта делает №4, аналитические модели и расчёты — №3, HTTP сохранения проверки — №5. С №1 согласовать зависимости миграций от `AUTH_USER_MODEL`; собственную модель пользователя не создавать.

## 2. Требования к данным

1. Спроектировать сущности из общих контрактов: Case, LandPlot, Event, Party, Relationship, Evidence, факты с происхождением, ImportBatch и Review. Добавить ограничения уникальности, внешние ключи и индексы под реальные запросы реестра и правил. Зафиксировать ER-схему и назначение ключей в `Code/docs/data-model.md`.
2. Разделить категорию земли, ВРИ и правообладателя; сохранять историю событий. Участок может участвовать в нескольких случаях; случай не равен кадастровому номеру. ИНН и кадастровые номера хранить строками, деньги/площади — Decimal. Поле даты присвоения кадастрового номера не заменяет дату приобретения права.
3. Сохранять происхождение значимых полей, исходные файл/лист/ячейку, реквизиты/ссылку документа, полноту и статус сверки. Расчётный факт содержит версию расчёта и ссылки на входы. Факт для анализа доступен по устойчивому ID и неизменяемой версии; изменение не разрушает старый запуск.
4. Не объединять лиц по фамилии, случаи по одному номеру участка или разные события по близости дат. Неустранимый конфликт возвращать явно; при сохранении противоречий оставлять обе версии и источники, без выбора «последняя строка верна».
5. Evidence может описывать ссылку или файл. Для файла — внутреннее имя сервера, исходное имя как метаданные, допустимый тип/размер, связь с конкретным фактом/случаем. Проверять URL-схему для ссылок; получать удалённый URL сервером не требуется. Защищённую выдачу делает №5. Публикация реального документа не следует автоматически из наличия его в таблице.
6. Историю Review делать добавочной: исходы из общих контрактов, обязательное непустое обоснование, связанные источники, серверные автор/время. Входные `author`/`created_at` клиента игнорируются. Проверять принадлежность документов и запуска случаю. Повтор формы с одним ключом не добавляет вторую запись.

## 3. Подготовка исходных таблиц

В пайплайне описаны И1, И2, И3, И4, И6, И8, И10: по 10 записей, всего 70 записей индикаторов, с повторами объектов. Это не 70 уникальных участков и не семь утверждённых правил MVP. В текущем пакете самих Excel нет. После получения провести инвентаризацию колонок и происхождения; жёлтый цвет переводить в `author_marked_real`, а не в «проверено».

Подготовить паспорт набора и таблицу соответствия «файл/лист/столбец → сущность/поле → тип → смысл пропуска → происхождение → правило-потребитель». И2 пока кандидат; И10 описывает лиц, И2 — документы/территории. Геометрию И8 не считать подтверждённой только из-за реальности кадастрового номера. Excel-формулы и «Да/Нет» сохраняются как расчётные данные, а не экспертный эталон.

Отдельно включить проверку расхождения по `61:14:0600009:1765`: в исходном описании встречаются 12.02.2026 как дата присвоения номера/регистрации и 19.02.2026 как тестовая дата регистрации. До документа не объединять эти даты в одно подтверждённое событие. Неподтверждённую дату не использовать как реальный факт покупки.

## 4. CSV и импорт

- До интеграции опубликовать полный CSV-словарь и три примера по разделу 4 общих контрактов. Примеры в Git — синтетические, с явной маркировкой и стабильными внешними ID; исходные персональные данные и файлы документов в Git не включать.
- Проверять заголовки, кодировку, структуру, типы, даты, единицы, длины и ссылки. Структурно корректный неполный пример принять с предупреждениями, чтобы №3 мог вернуть `insufficient_data`. Неизвестное обязательное для анализа поле не равно структурно неверному CSV.
- Номер строки, поле и стабильный код ошибки возвращать сервисом. Минимальные коды: `INVALID_HEADER`, `INVALID_ENCODING`, `INVALID_DATE`, `INVALID_VALUE`, `UNKNOWN_REFERENCE`, `CONFLICTING_FACT`, `FILE_TOO_LARGE`, `TOO_MANY_ROWS`. Сообщения — по-русски, технический traceback пользователю не выдавать.
- Сначала полностью валидировать пакет, затем записывать предметные данные в одной транзакции. Ошибка последней строки не оставляет сохранённую первую. Запись отклонённого ImportBatch и ошибок разрешена.
- Реализовать согласованную политику дублей из общих контрактов, checksum/idempotency key и ограничения БД. Проверить повтор одного файла, частичное пересечение нового файла и конкурентную загрузку. Импорт не перезаписывает старые факты и результаты анализа.
- Публиковать `ImportOutcome` для №4 и сервис чтения фактов для №3. Повтор не выглядит как новая успешная вставка: пользователь видит исходную загрузку и счётчик дублей.

## 5. Демоданные, история и восстановление

Совместно с №3 подготовить минимум 15 контрольных сценариев: 5 заданных сочетаний риска, 5 обычных изменений, 5 неполных/противоречивых/неприменимых. Дополнительно — пример за пределами периода и без изменения ВРИ. Включить источники-заглушки, явно названные демонстрационными; демонстрационная связь не становится реальной из-за реального номера участка.

Сделать команду `python manage.py load_demo_data` или равнозначную документированную команду. Повтор команды не размножает данные и не удаляет пользовательские записи. Опасная очистка не выполняется по умолчанию. Передать №5 case ID показательных примеров и ожидаемое происхождение фактов.

До 19 ноября проверить восстановление согласованной копии MySQL и вложений в отдельную БД/каталог, передать №1 сведения о восстановлении; не проверять восстановление поверх единственного стенда. Секреты и дампы не коммитить. Проверка запуска восстановленной версии — совместно с №1.

## 7. Приёмка

- [ ] Миграции проходят на пустой MySQL и при обновлении предыдущей рабочей версии; нет незафиксированных изменений моделей.
- [ ] Кириллица, строковые идентификаторы, Decimal и разные состояния неизвестности сохраняются без искажений.
- [ ] Ошибка в конце CSV не оставляет предметных строк; ошибки содержат корректные номера.
- [ ] Идентичный, пересекающийся и конкурентный импорт не создают скрытых дублей; конфликт не перезаписывает данные.
- [ ] Для результата правила можно получить ровно те версии фактов и источников, которые он использовал.
- [ ] Синтетика и происхождение расчётных входов доходят до №3 и интерфейса без потерь.
- [ ] Повтор POST Review не создаёт дубль, новая проверка сохраняет предыдущую; автор и время серверные.
- [ ] Демо загружается повторяемой командой; восстановленная копия пригодна для запуска.

Проверки должны работать с MySQL в CI. Проверяющий №1 повторяет импорт, конфликт и восстановление по инструкции; результаты на одной SQLite не подтверждают приёмку.
